## 2. Multi-Bot Architecture

### 2.1 When to Run Multiple Bots

Multiple bot instances become valuable when:

- **Different strategies**: e.g., one trend-following bot (12h scans) and one mean-reversion bot (1h scans)
- **Different exchanges**: Binance spot, Binance futures, Bybit, etc.
- **Different timeframes**: Long-term (4h candles) vs short-term (15m candles)
- **Risk isolation**: One bot crashing should not affect others
- **Separate capital pools**: Different risk profiles per strategy

The current Cryptonita setup (single V4 ensemble, 39 coins, 12h scan + 5min monitor) does **not** need multi-bot architecture yet. This becomes relevant when adding a second strategy or exchange.

### 2.2 Shared vs Separate Databases

| Approach | Pros | Cons | When to Use |
|---|---|---|---|
| **Shared DB, separate schemas** | Single backup point, cross-bot analytics, lower cost | Schema conflicts, single point of failure | 2-3 bots, same developer |
| **Shared DB, same schema** | Simplest, add `bot_id` column to trades/positions | Coupling, harder to evolve independently | Bots with identical data models |
| **Separate databases** | Full isolation, independent migrations, can scale individually | Higher cost, harder to aggregate analytics | Different teams, different strategies |

**Recommendation for solo developer:** Shared database with a `bot_id` column on `trades`, `positions`, and `signals` tables. Keep it simple. Separate schemas only when strategies diverge significantly.

### 2.3 Inter-Bot Communication

| Method | Latency | Complexity | When to Use |
|---|---|---|---|
| **PostgreSQL LISTEN/NOTIFY** | ~1-10ms | Low | Already have PG; simple event broadcasting |
| **Redis Pub/Sub** | ~sub-ms | Medium | Need fast messaging; shared state/caching |
| **HTTP API calls** | ~1-50ms | Low | Bots on different machines |
| **Shared filesystem (JSON/SQLite)** | ~1-10ms | Very low | Prototype/testing only |

**Recommendation:** Start with **PostgreSQL LISTEN/NOTIFY** -- zero additional infrastructure. The current setup already has PostgreSQL. Example use case: Bot A opens a position, Bot B gets notified to avoid duplicate exposure to the same ticker.

```python
# Publisher (in trading_bot.py after opening position)
await db.execute("NOTIFY position_opened, 'BTCUSDT'")

# Subscriber (in another bot)
await db.execute("LISTEN position_opened")
# async loop to receive notifications
```

Only add Redis when you need sub-millisecond pub/sub, shared caching (e.g., orderbook state), or rate limiting across bots.

### 2.4 Process Management

| Tool | Setup Effort | Auto-restart | Logging | Resource Limits | Best For |
|---|---|---|---|---|---|
| **docker-compose** | Medium | Yes | Built-in | Yes (memory, CPU) | **Recommended** for VPS |
| **systemd** | Low | Yes | journald | cgroups | Native Linux, no Docker |
| **supervisord** | Low | Yes | File-based | No | Legacy, maintenance mode |
| **PM2** | Low | Yes | Built-in | Yes | Node.js ecosystems |

**Recommendation:** Use **docker-compose** when moving to VPS. It provides:
- Isolated containers per service (bot, API, PostgreSQL, Redis)
- Easy restart policies (`restart: unless-stopped`)
- Memory limits per container to prevent OOM cascades
- Simple `docker-compose up -d` deployment
- Portable across VPS providers

Example docker-compose structure for Cryptonita:

```yaml
services:
  api:
    build: .
    command: python run_api.py
    ports: ["8000:8000"]
    restart: unless-stopped
    mem_limit: 512m
    depends_on: [db]

  bot:
    build: .
    command: python run_bot.py
    restart: unless-stopped
    mem_limit: 1g   # More RAM for ML model
    depends_on: [db]

  db:
    image: postgres:16-alpine
    volumes: ["pgdata:/var/lib/postgresql/data"]
    mem_limit: 512m

  # Future: add Redis, second bot, nginx
```

## 3. WebSocket vs REST for Market Data

### 3.1 Current Architecture

The current bot uses **REST polling** via the Binance API:
- `scan_interval_hours: 12` -- full market scan every 12 hours
- `position_monitoring_minutes: 5` -- check open positions every 5 minutes
- Uses `ccxt` (REST) through `BinanceService` and `BinanceDataService`
- Each scan fetches OHLCV candles for 39 coins sequentially

**REST polling costs:** ~39 API calls per scan cycle (one per coin for OHLCV), plus price checks every 5 minutes for open positions (up to 10 calls). Roughly 50-100 calls per hour. Binance allows 1,200 requests/minute, so rate limits are not a concern.

### 3.2 WebSocket Benefits

| Metric | REST Polling (Current) | WebSocket |
|---|---|---|
| **Signal detection latency** | 12 hours (scan interval) | Real-time (<1 second) |
| **Position monitoring latency** | 5 minutes | Real-time (~20ms) |
| **API calls per hour** | 50-100 | 0 (persistent connection) |
| **Rate limit risk** | Low (current), grows with more coins | None |
| **Data freshness for dashboard** | 5-minute snapshots | Live prices |
| **Connection overhead** | New TCP handshake each request | One persistent connection |

### 3.3 Binance WebSocket Streams

Relevant streams for Cryptonita:

| Stream | Data | Use Case | Bandwidth |
|---|---|---|---|
| **`<symbol>@kline_<interval>`** | Real-time candlestick updates | Signal generation on candle close | Low (~1 msg/sec per pair) |
| **`<symbol>@ticker`** | 24h price statistics | Position monitoring, dashboard | Medium (~1 msg/sec) |
| **`<symbol>@miniTicker`** | Compressed price data | Price-only monitoring | Low |
| **`!miniTicker@arr`** | All tickers in one stream | Monitor 39+ coins efficiently | Medium |
| **`<symbol>@depth<levels>`** | Order book snapshots | Liquidity analysis (future) | High |

**Key insight:** The `!miniTicker@arr` stream sends all market tickers in a single message every second. This means monitoring 39 coins requires **one** WebSocket connection, not 39.

### 3.4 Implementation with CCXT Pro

CCXT Pro extends ccxt with unified WebSocket support:

```python
import ccxt.pro as ccxtpro

async def watch_prices():
    exchange = ccxtpro.binance({'enableRateLimit': True})
    symbols = ['BTC/USDT', 'ETH/USDT', ...]  # 39 coins

    while True:
        # Watches all tickers via a single combined stream
        tickers = await exchange.watch_tickers(symbols)
        for symbol, ticker in tickers.items():
            await process_price_update(symbol, ticker)

    await exchange.close()
```

**CCXT Pro considerations:**
- Requires `pip install ccxt` (WebSocket support included in current versions)
- Uses asyncio event loop -- compatible with current bot's `async` architecture
- Handles reconnection automatically
- Maintains incremental state in memory (orderbook, tickers, OHLCV)
- Supports `watch_ohlcv()` for real-time candle updates

### 3.5 Memory Impact

| Component | Memory Estimate | Notes |
|---|---|---|
| **WebSocket connection (1)** | ~5-10 MB | Single connection for all streams |
| **Ticker cache (39 coins)** | ~1-2 MB | In-memory incremental structures |
| **OHLCV cache (39 coins x 100 candles)** | ~10-20 MB | If watching candle streams |
| **Order book cache (if used)** | ~50-100 MB | Not needed for current strategy |
| **Total WebSocket overhead** | ~20-30 MB | Negligible vs REST approach |

WebSocket adds minimal memory overhead. The main concern is the asyncio event loop sharing CPU with the bot's scan logic, but Python's async model handles this well for I/O-bound work.

### 3.6 Handling Disconnections

WebSocket connections will drop due to network issues, server maintenance, or Binance's 24-hour connection limit. Robust handling is essential:

```python
class WebSocketManager:
    def __init__(self):
        self.exchange = None
        self.reconnect_delay = 1  # seconds, exponential backoff
        self.max_reconnect_delay = 60

    async def connect_with_retry(self):
        while True:
            try:
                self.exchange = ccxtpro.binance({...})
                self.reconnect_delay = 1  # Reset on success
                await self.watch_loop()
            except (NetworkError, ExchangeNotAvailable) as e:
                logger.warning(f"WebSocket disconnected: {e}")
                await asyncio.sleep(self.reconnect_delay)
                self.reconnect_delay = min(
                    self.reconnect_delay * 2,
                    self.max_reconnect_delay
                )
            finally:
                if self.exchange:
                    await self.exchange.close()
```

**Best practices:**
- Exponential backoff on reconnect (1s, 2s, 4s, ... up to 60s)
- Fall back to REST polling during prolonged WebSocket outages
- Log all disconnections for post-mortem analysis
- Binance forces disconnect after 24 hours -- rotate connections proactively

### 3.7 WebSocket Migration Recommendation

**Do not migrate to WebSocket immediately.** The current 12h scan + 5min monitor architecture is adequate for the strategy's timeframe. WebSocket becomes valuable when:

1. Moving to shorter timeframes (15m, 1h candles) where 12h scan intervals miss opportunities
2. Adding real-time dashboard with live price updates
3. Monitoring 80+ coins where REST polling approaches rate limits
4. Implementing trailing stop-losses that need sub-second price feeds

**Priority: Medium.** Implement after VPS migration and monitoring setup. Estimated effort: 8-12 hours.

## 4. Database Scaling

### 4.1 Current State

- **PostgreSQL on Render free tier**: 256MB RAM, 1GB storage, expires after 30 days
- **Tables**: positions, trades, signals, training_history, OHLCV cache
- **Current data volume**: Small (weeks of data for 39 coins)

### 4.2 Storage Growth Estimation

| Data Type | Per Coin/Day | 39 Coins/Day | 80 Coins/Day | Annual (80 coins) |
|---|---|---|---|---|
| **OHLCV (5m candles)** | 288 rows x ~100 bytes = 28 KB | 1.1 MB | 2.3 MB | 830 MB |

### 4.3 When to Upgrade What

| Trigger | Action | Cost Impact |
|---|---|---|
| **Free DB expires (30 days)** | Migrate to Render Starter DB ($7/month) or self-hosted PG on VPS ($0 extra) | $0-7/month |
| **Storage >5 GB** | Add partitioning by month on OHLCV table | $0 (code change) |

| **Read-heavy dashboard + write-heavy bot** | Read replica (only if >1000 QPS) | $4-7/month (second PG instance) |

### 4.4 Time-Series Optimization Strategies

**Immediate (free):**
```sql
-- Partition OHLCV by month
CREATE TABLE ohlcv_data (
    id SERIAL,
    ticker VARCHAR(20),
    timestamp TIMESTAMPTZ,
    open DECIMAL, high DECIMAL, low DECIMAL, close DECIMAL, volume DECIMAL
) PARTITION BY RANGE (timestamp);

CREATE TABLE ohlcv_2026_04 PARTITION OF ohlcv_data
    FOR VALUES FROM ('2026-04-01') TO ('2026-05-01');

-- Composite index for common query pattern
CREATE INDEX idx_ohlcv_ticker_time ON ohlcv_data (ticker, timestamp DESC);
```

**Later (if needed):**
- **TimescaleDB extension**: Automatic partitioning (hypertables), continuous aggregations, compression (10-20x). Free extension, installs on any PG. 20x faster inserts at scale.
- **Materialized views**: Pre-compute daily/weekly aggregates for dashboard charts.

### 4.5 Connection Pooling

**Current state:** Single gunicorn worker + single bot process = 2-5 concurrent connections. PgBouncer is not needed yet.

**When to add PgBouncer:**
- Multiple bot instances (3+ processes connecting to PG)
- Multiple API workers (scaling gunicorn to 2-4 workers)
- Connection count approaching `max_connections` (default 100)

PgBouncer adds virtually zero memory (~2MB) and is trivial to configure on a VPS:
```ini
[databases]
cryptonita = host=127.0.0.1 dbname=cryptonita_production

[pgbouncer]
pool_mode = transaction
max_client_conn = 100
default_pool_size = 10
```

### 4.6 Database Recommendation

**Phase 1:** Self-host PostgreSQL on VPS (included in Hetzner $4.10/month). No extra cost.
**Phase 2:** Add monthly partitioning when OHLCV data exceeds 1GB.
**Phase 3:** Install TimescaleDB extension when storing 5-minute candles for 50+ coins.
**Phase 4 (unlikely needed):** PgBouncer when running 3+ concurrent processes.

## 5. Monitoring and Alerting

### 5.1 Health Check Endpoints

The current `render.yaml` already defines `healthCheckPath: /health`. Expand this to a comprehensive health system:

```python
# src/api/routes/health.py

@router.get("/health")
async def health_check():
    """Basic health check -- returns 200 if API is alive."""
    return {"status": "ok"}

@router.get("/health/detailed")
async def detailed_health():
    """Deep health check for monitoring dashboards."""
    checks = {}

    # Database connectivity
    try:
        await db.execute("SELECT 1")
        checks["database"] = {"status": "ok", "latency_ms": latency}
    except Exception as e:
        checks["database"] = {"status": "error", "error": str(e)}

    # Bot status
    bot_status = bot_manager.get_status()
    checks["bot"] = {
        "status": "running" if bot_status.is_running else "stopped",
        "last_scan": bot_status.last_scan_time,
        "open_positions": len(bot_status.positions),
        "cycle_number": bot_status.cycle_number,
    }

    # Model status
    checks["model"] = {
        "version": "V4",
        "loaded": predictor.is_loaded,
        "last_training": predictor.last_training_date,
    }

    # Memory usage
    import psutil
    process = psutil.Process()
    checks["system"] = {
        "memory_mb": process.memory_info().rss / 1024 / 1024,
        "cpu_percent": process.cpu_percent(),
    }

    overall = "ok" if all(
        c.get("status") in ("ok", "running") for c in checks.values()
    ) else "degraded"

    return {"status": overall, "checks": checks}
```

### 5.2 Telegram Alerts (Recommended -- Free, Instant)

Telegram is the dominant notification channel for crypto trading bots. Setup requires:
1. Create a bot via @BotFather (free, 2 minutes)
2. Get your chat ID
3. Add a lightweight notification service

```python
# src/services/telegram_notifier.py

import httpx
from config import settings

class TelegramNotifier:
    BASE_URL = "https://api.telegram.org/bot{token}"

    def __init__(self):
        self.token = settings.TELEGRAM_BOT_TOKEN
        self.chat_id = settings.TELEGRAM_CHAT_ID
        self.enabled = bool(self.token and self.chat_id)

    async def send(self, message: str, parse_mode: str = "HTML"):
        if not self.enabled:
            return
        async with httpx.AsyncClient() as client:
            await client.post(
                f"{self.BASE_URL.format(token=self.token)}/sendMessage",
                json={
                    "chat_id": self.chat_id,
                    "text": message,
                    "parse_mode": parse_mode,
                }
            )

# Usage throughout the bot:
notifier = TelegramNotifier()

# Trade executed
await notifier.send(
    f"<b>BUY</b> {ticker}\n"
    f"Price: ${entry_price:.4f}\n"
    f"Size: ${position_size:.2f}\n"
    f"Confidence: {confidence_level}\n"
    f"SL: ${stop_loss:.4f} | TP1: ${tp1:.4f}"
)

# Circuit breaker triggered
await notifier.send(
    f"CIRCUIT BREAKER ACTIVATED\n"
    f"Drawdown: {drawdown_pct:.1%}\n"
    f"Action: {action}"
)

# Model promoted after retraining
await notifier.send(
    f"MODEL PROMOTED\n"
    f"Sharpe: {sharpe:.2f} (was {old_sharpe:.2f})\n"
    f"Win Rate: {win_rate:.1%}"
)
```

| Stop-loss triggered | High | Per event |
| Take-profit hit (TP1/TP2/TP3) | Medium | Per event |
| Circuit breaker activated | Critical | Rare |

| Model retrained & promoted | Medium | Weekly |
| Daily P&L summary | Low | Daily |

```python
# At end of each scan cycle in trading_bot.py
async def _ping_healthcheck(self):
    """Ping healthchecks.io to confirm bot loop is alive."""
    if settings.HEALTHCHECK_PING_URL:
        async with httpx.AsyncClient() as client:
            await client.get(settings.HEALTHCHECK_PING_URL, timeout=10)
```

### 5.4 Log Aggregation

**On Render:** Logs are available in the dashboard, but limited retention (72 hours on free/starter).

**On VPS (recommended setup):**
- **Loguru** (already in use): File rotation, structured logging
- Store logs on disk with `rotation="1 day"`, `retention="30 days"` (already configured)
- For searchable logs: pipe to a free Grafana Cloud Loki instance (50GB free)
- Alternative: simple `grep`/`tail` on log files via SSH for a solo developer

**Recommendation:** Loguru file logging on VPS is sufficient for a solo developer. Add Grafana Cloud Loki only if debugging production issues frequently.

### 6.2 Deployment Strategies

#### On Render (Current)

Render already provides near-zero-downtime deploys:
- Push to `main` -> Render builds new image -> health check passes -> swap traffic
- If health check fails, old version stays live
- Rollback: Redeploy previous commit from dashboard

**This is sufficient for the current setup.** No changes needed.

#### On VPS (After Migration)

For a solo developer on a VPS, keep it simple:

**Strategy A: Git Pull + Restart (Simplest)**
```bash
#!/bin/bash
# scripts/deploy.sh
set -e
cd /opt/cryptonita
git pull origin main
docker-compose build --no-cache
docker-compose up -d
docker-compose ps  # Verify services are running
echo "Deploy complete at $(date)"
```
- Downtime: 10-30 seconds during restart
- Acceptable for a trading bot (5-minute monitoring interval means no missed signals)
- Positions are loaded from DB on restart (already implemented in `_load_positions_from_db`)

**Strategy B: Blue-Green with Docker (Low Complexity)**
```bash
#!/bin/bash
# scripts/deploy-blue-green.sh
set -e
cd /opt/cryptonita

# Build new version
docker-compose -f docker-compose.blue.yml build

# Start new version on alternate port
docker-compose -f docker-compose.blue.yml up -d

# Wait for health check
sleep 5
curl -f http://localhost:8001/health || exit 1

# Swap nginx upstream
ln -sf /etc/nginx/conf.d/blue.conf /etc/nginx/conf.d/active.conf
nginx -s reload

# Stop old version
docker-compose -f docker-compose.green.yml down
```
- Zero downtime for the API
- Bot needs graceful handoff (drain open orders before stopping old instance)
- Overkill for a solo developer unless uptime is critical

**Recommendation:** Strategy A (git pull + restart) is the right choice. The bot survives restarts via DB-backed position state. Add blue-green only if running with real money and zero-downtime becomes essential.

### 6.3 Rollback Strategies

| Scenario | Rollback Method | Time |
|---|---|---|
| Bad deploy on Render | Click "Manual Deploy" with previous commit SHA | ~2 min |
| Bad deploy on VPS | `git revert HEAD && ./deploy.sh` | ~1 min |
| Bad model promotion | Auto-trainer already keeps previous model; rollback via DB flag | ~30 sec |
| DB migration failure | Keep migration scripts idempotent; manual `ALTER TABLE` if needed | ~5 min |

**Key principle:** Always keep the previous working state recoverable. Tag releases (`git tag v3.1.0`) before deploying.
